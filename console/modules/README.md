# Implementing a module

`GetUserSPNs.py` is the first (and so far only) module wired up end to end:
listed, selectable, configurable, and runnable. This is the pattern to
repeat for the rest of the catalog.

## How a module goes from "in modules.json" to "runnable"

1. **`console/modules.json`** describes every impacket example script:
   its required/optional flags, help text, and whether each optional flag
   takes a value (`"takes_value": false` for boolean switches like
   `-debug`). It's generated by `console/generate_modules.py`, which
   statically parses `examples/*.py` - rerun it after pulling upstream
   impacket changes so flags stay accurate.
2. **`console/Options.py`** has one attribute per unique flag across every
   module (see `FlagUtils.flag_to_attr` for the flag -> attribute name
   rule). `use <module>` gives the console a fresh `Options()` instance;
   `set <option> <value>` fills in attributes on it.
3. **`console/modules/base.py`**'s `ModuleRunner` turns a module's
   `modules.json` entry + its `Options` instance into an argv and runs the
   script as a subprocess. The default implementation is generic - it just
   walks the required/optional flag lists - so most modules won't need to
   override anything.
4. **`console/modules/__init__.py`**'s `MODULE_RUNNERS` dict maps a
   `modules.json` "name" (e.g. `"GetUserSPNs.py"`) to the `ModuleRunner`
   subclass that runs it.
5. **`"implemented": true`** in a module's `modules.json` entry is what
   makes it show up in `list`/`search` (without `-a/--all`) and lets `run`
   execute it. This field is hand-curated and survives
   `generate_modules.py` reruns.

## Adding the next module

1. Pick a module and check its `modules.json` entry looks right (correct
   required vs. optional flags, sane `takes_value`). Fix `generate_modules.py`
   first if the extraction is wrong for a whole class of scripts - don't
   hand-edit generated data, it'll be overwritten on the next run.
2. Decide if the generic `ModuleRunner` is enough. It is, if the module is
   "build an argv from flags and exec it" like `GetUserSPNs.py`
   (`console/modules/get_user_spns.py` - a no-override subclass, copy it as
   your starting point). It isn't, if the module needs things like:
   - an interactive shell after launch (`wmiexec.py`, `psexec.py`, ...)
   - output that should be parsed/reformatted rather than streamed raw
     (`secretsdump.py`, `GetADUsers.py`, ...)
   - cross-flag validation beyond "is it set" (e.g. `dpapi.py`'s several
     mutually exclusive subcommands)
   - credential/value prompting or transformation before launch

   For those, subclass `ModuleRunner` and override `validate()` and/or
   `build_argv()` (see the docstrings in `base.py`).
3. Register the class in `MODULE_RUNNERS` in `console/modules/__init__.py`.
4. Flip `"implemented": true` for that module in `console/modules.json`.
5. Add tests under `console/tests/` alongside `test_module_runner.py`.
6. Sanity check with `use <module>`, `set` the required options, `run` -
   with a target you don't mind actually hitting, since `run` launches the
   real impacket script.

## What's deliberately still generic / not module-specific

- `do_run` in `console.py` doesn't know anything about individual modules;
  it just asks the registry for a runner and calls `validate()`/`build_argv()`.
- Output is currently streamed straight to the console's stdio (the
  subprocess inherits them), so password prompts etc. from the underlying
  script work interactively. If a module needs to post-process output
  instead, that's a reason to override more of `ModuleRunner` (e.g. capture
  output in `build_argv`'s caller) rather than special-casing it in
  `console.py`.
